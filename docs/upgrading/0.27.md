# Upgrading to 0.27

0.27 refuses query-builder values it does not know instead of writing them into SQL.

## From 0.26

The builder (the main read, `distinct()` and `groupBy()`) now checks, at the read, what it writes into SQL as text. A restricted read of an access-governed table, which applies these in JS, refuses the same values:

| Position | Accepted | Anything else |
|----------|----------|---------------|
| `where`/`whereAny`/`having` operator | `=` `!=` `<` `>` `<=` `>=` `IN` | `ArgsError` |
| `order(column, dir)` | `"asc"`, `"desc"` (lowercase) | `ArgsError` |
| `limit(n)`, `offset(n)` | a non-negative safe integer | `ArgsError` |
| `groupBy(columns, aggs)` aggregate | `"count"`, `[sum\|avg\|min\|max\|countDistinct, column]` | `ArgsError` |

`ArgsError` is exported from the package root. It is an `HttpError` with status 400, so a call that hits it answers 400.

Code that keeps to the builder's types needs no change. What breaks is an untyped value reaching the builder, most often an operation's arg passed straight through: a `limit` that arrives as `"20"`, a direction sent as `"DESC"`, a negative or fractional offset. Convert such args before the builder (`Number(args.limit)`, checked) or declare and check them at the operation.

A limit of `-1` as "no limit" is refused too: leave the limit unset instead.

The SQL the builders write now spells the direction `ASC`/`DESC`; only tests that compare SQL text notice.
